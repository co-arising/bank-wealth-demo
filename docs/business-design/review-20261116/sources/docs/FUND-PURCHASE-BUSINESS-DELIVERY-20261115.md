# 基金购买：有业务内容的最小可执行交付

记录日期：2026-11-15。
状态：**用户目标与协作授权已记录；业务方案、政策、用例和实现尚待逐项形成与验证。** 不是生产金融认证、法律合规意见或任何真实机构的批准。

## 1. 用户明确的目标

用户要求最小交付是“大概真实的有血有肉的可执行的代码”，并指出：如果用例逻辑不清晰，应补充丰富用例逻辑，不能只留下参数校验、空壳胶水与机械事件构造。

主agent负责接受目标、组织场景与角色、让不同角色提出方案和挑战、综合取舍并交付；用户提供token，授权使用虚拟角色agent。角色应包括方案设计者、不同背景的挑战者、业务专家、基金公司业务对接负责人、银行业务负责人、技术架构师、研发负责人、验收测试负责人，并可按实际需要补充。

这不是让虚拟评审代替真实监管/机构/法务签收。所有角色结论必须标明模拟、假设、建议或已确认规则，不能伪造现实专家参与记录。

## 2. 与生成器主线的关系

主线不变：**Scala清单 → JS A/B分区 → 逐ArtifactType内容级diff → 按diff对齐实现**。生成器侧要求见 [代码内容评审记录](../../metarch-truthsrc/docs/codegen-parity/REVIEW-AND-DELIVERY-DECISIONS-20261115.md)。

业务内容与生成器质量相辅相成：
- 清楚的业务用例、规则和异常路径是输入，不能由模板根据散文猜测。
- A按对应Scala内容与用户明确质量要求复刻，B按同一目录/OO + Plain FP标准设计。
- 生成代码既要能执行，也应让业务/技术读者沿着“请求→规则→决定→事件→状态→结果”读通。
- 已有工业级库机制应正确复用，不能给每个业务重新生成一套Actor缓存或流程调度器来掩盖缺失的业务模型。

当前工作只记录要求和保存上下文，不改作者树/绑定/金融oracle、不写业务实现、不改生成器。

## 3. 推荐的虚拟角色阵容

以下为**后续组织方案**，尚未实际召开，也不是已得到这些角色的结论。主agent负责控制人数、主题和成本，不把角色数等同质量。

| 角色 | 负责提出/核查什么 | 主要反对什么 |
|---|---|---|
| 方案设计者/主agent | 有边界的购买与定投方案、完整用例步骤、裁决与依赖 | 目标漂移、只堆文档/技术机制 |
| 银行财富业务负责人 | 客户受理、银行销售与扣款责任、客户/运营可见状态 | 用技术状态替代业务承诺 |
| 基金公司/TA业务对接负责人 | 申购受理/拒绝、确认结果、外部请求身份、重复/迟到/对账 | 将付款成功当份额确认、编造TA行为 |
| 基金产品/交易规则专家 | 金额/份额/NAV/费用/日期与产品规则是否自洽 | 无依据的统一规则、舍入和计价含糊 |
| 银行支付/账务/清算专家 | 资金预留、扣减/入账、退款独立性、账务守恒与差错处理 | 重复扣款、账实不符、已commit付款被当TCC补偿撤销 |
| 运营/对账/异常处理负责人 | 超时、未知结果、迟到回执、重试与人工处理、查询解释 | 一切失败都当可重试或自动成功 |
| 客户/渠道体验挑战者 | 用户意图、重复点击、取消/修订、状态和错误文案 | 流程可运行但客户无法理解/恢复 |
| 来自不同业务背景的挑战者 | 用另一类交易/长流程经验提出反例，检验边界是否过度银行特化 | 过拟合演示脚本、通用名词掩盖业务差异 |
| 技术架构师 | DDD边界、Event Sourcing/CQRS/Saga/Monarch各自职责、依赖与身份 | 过度编排、无意义层次、机制泄漏进纯领域 |
| 研发团队负责人 | 可读代码、局部修改成本、清晰胶水、库复用与维护所有权 | 巨型表达式、FQN泛滥、转发迷宫、模板不可演进 |
| 验收测试负责人 | 独立正反例、资金/状态oracle、失败恢复和覆盖闭环 | 自测自证、只验happy path或生成shape |
| 合规/适当性风险挑战者（按场景启用） | 明确哪些前置需要建模，哪些属于demo排除项/真实机构责任 | 虚构法规、把模拟审批当真实批准 |

初轮先让关键角色独立提出问题，再由设计者综合，避免所有人先读同一份答案形成表面共识。角色可以合并执行，但观点职责应可区分。

## 4. 后续工作坊的产物，不只是一轮聊天

每个保留用例应形成：
1. 业务目标、参与者、触发、前置和完成条件；
2. 正常步骤：谁决定什么、调用什么边界、产生什么业务事实；
3. 替代/失败路径：重复、冲突、余额不足、拒绝、超时、未知、迟到与人工处理；
4. 明确规则：字段语义、金额/单位/精度、状态转移、业务与技术身份、时间口径；
5. 命令→业务参数→规则/计算→事件→状态→回复/查询结果；
6. 外部接口请求/应答/查询/重放与mock行为合同；
7. 独立可执行场景（Given/When/Then及数据oracle），覆盖每个需要交付的行为port/实现，不只纯函数；
8. 规则/用例/实现/测试/生成制品/回锚的对应关系；
9. 被拒方案、理由、未决问题和范围外项；
10. 真实执行证据与剩余缺口，未运行不可标PASS。

方案不能只给“校验后生成Event”的模板；应让人读懂为何允许、拒绝或幂等返回，以及这个事实在业务上承诺了什么。

## 5. 首批应澄清的业务问题（未决，不是新政策）

围绕现金申购、有限定投、TA确认/拒绝与独立退款，核当前真源已有答案，再填真正缺口：
- 请求受理、计划创建/激活、扣款、申购受理、份额确认各自含义与边界；
- 交易日/受理时点/确认时点如何表达，哪些真实规则在demo中简化并明确标注；
- 客户及产品前置是否需要显式建模，哪些是可信demo账户假设；
- 支付与TA对接之间的未知状态如何查询/对账，何时可重试、何时需要人工；
- 相同请求、不同请求同ID、同一期次重复触发怎样区分；
- 净值、份额、费用与舍入规则从哪里来，确认金额如何对齐已扣金额；
- TA拒绝后独立退款如何幂等、可观测；不能混同已提交支付的补偿；
- 定投配置修订/暂停/恢复对未来与已发起期次的影响；
- 客户、银行运营和基金公司分别观察/负责哪些状态。

这些问题需角色互相挑战后形成有根据的模拟业务方案。不能把“需要讨论”写成“现实银行必定采用某规则”，也不能将不清晰部分硬编码进生成器。

## 6. 授权、所有权与边界

- 主agent已获组织虚拟角色/并发agent的方向授权；应分题、限定写集合、逐份保存、控制中转站RPM/TPM，网络抖动按用户要求可重试。不得因为重试重跑已成功的业务owner或覆盖既有文件。
- 业务事实、用例、绑定、mock与独立oracle留银行仓；通用编译/生成/回锚能力留公共工具仓。另一`mad-polaris-business-expression`会话的公共业务表达设计有独立owner；接续公共语法时先读其指引和唯一设计，不复制第二套schema或越权接管。
- Agent写的业务实现/测试同属手写维护所有权，不因AI生成就可被模板覆盖；能够完整确定性生成的行为不一刀切迁出。
- 延续已确认demo边界：基金公司/TA可mock或模拟，不能将真实外部集成当完成前置；模拟仍须保留契约和业务结果。既有有限定投不静默删除。
- 接近真实的可执行demo不等生产金融系统，不自动扩成完整银行账户、全持仓、监管/生产认证；如业务丰富需要改变范围，明确列出取舍，不用无数小guard无限加批。
- 不自动获得真实资金操作、对外联系、外部服务发布、commit/push/tag/release、运行库重发、BC默认切流或共享应用写入授权。
